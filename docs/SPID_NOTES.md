## The lines we ship

```
Item = 0x800~CardboardFaceMask.esp|ActorTypeNPC|NONE|NONE|-C|1|100
Keyword = KEFEquip_0x800_CardboardFaceMask_esp|ActorTypeNPC|NONE|NONE|-C|NONE|100
```

Generated by `src/07_package.py` (`distribution_lines`) from `config.yaml`: `plugin_name`,
`exclude_children` (true -> `-C`, false -> `NONE`), `chance_percent` (100 as is; below 100 with a
trailing `!`, e.g. `25!`, see section 7) and `equip_method`; the item count is fixed at 1.

* The `Item` line puts the mask into the inventory (sections 1-8). SPID never equips it (section 9).
* The `Keyword` line (only with `equip_method: kef`, the default) gives the same NPCs a keyword that
  SPID creates at runtime and that KEF turns into "wear item 0x800 of CardboardFaceMask.esp"
  (section 13). With `equip_method: engine` the ini has the `Item` line only.
* Both lines carry the same filters and chance. Below 100 % they would roll independently (section
  13), so then the `Keyword` line carries the chance and the `Item` line uses the keyword as its
  string filter at 100 %:
  ```
  Item = 0x800~CardboardFaceMask.esp|KEFEquip_0x800_CardboardFaceMask_esp|NONE|NONE|-C|1|100
  Keyword = KEFEquip_0x800_CardboardFaceMask_esp|ActorTypeNPC|NONE|NONE|-C|NONE|25!
  ```

These are the only active lines in `CardboardFaceMask_DISTR.ini`; the file's comment header says
what each line does (and that the keyword needs KEF), explains every field and shows three
commented example variants. `src/07_package.py` validates the shipped file against these rules.

## 1. File discovery and INI syntax

* SPID scans `Data\` for files with extension exactly `.ini` whose path contains `_DISTR`
  (case-sensitive `rfind`): `LookupConfigs.cpp:94` -> CLibUtil `distribution.hpp:29-46`
  (`std::filesystem::directory_iterator`, i.e. **not recursive**: the ini must sit directly in Data).
  Files are processed in sorted order (`distribution.hpp:43`).
* Only the global (section-less) part of the ini is read: `ini.GetSection("")`
  (`LookupConfigs.cpp:117`). A `[Section]` header would hide every entry below it.
* SimpleIni treats lines starting with `;` or `#` as comments (CLibUtil
  `detail/SimpleIni.h:1247-1248`). There are no inline comments, so comments go on their own line.
  Several `Item =` keys are allowed (`SetMultiKey`, `LookupConfigs.cpp:110`).
* Before parsing, each value is "sanitized": without a `~` in the value the first ` - ` becomes
  `~`, spaces around `|` and `,` are removed, `00012345` becomes `0x12345` and leading zeros after
  `0x` are dropped (`LookupConfigs.cpp:13-53`). If that changed anything, **SPID rewrites the ini
  file on disk** (`LookupConfigs.cpp:140-158`). Our lines have nothing to sanitize, so the shipped
  file is never rewritten: the package validator runs a copy of these rules (`spid_sanitize`) on
  every active line.

## 2. Field order of `Item = ...`

The key selects the record type: an optional `Final` prefix is stripped, then the name is looked up
in `{Form, Spell, Perk, Item, Shout, LevSpell, Package, Outfit, Keyword, Faction, SleepOutfit, Skin}`
(`LookupConfigs.h:338-355`, names at `LookupConfigs.h:61-74`; `Keyword` at line 70). `Item` and
`Keyword` lines go through the same parsers. The value is split on `|`
(`Parser.h:67`) and the sections are handed, in order, to these parsers (`LookupConfigs.cpp:59-67`;
the same order is spelled out in `Defs.h:3`):

| # | Section | Parser | Ours |
|---|---|---|---|
| 1 | FormOrEditorID | `DistributableFormComponentParser` (`LookupConfigs.h:357-365`) | `0x800~CardboardFaceMask.esp` |
| 2 | StringFilters | `StringFiltersComponentParser` (`LookupConfigs.h:367-397`) | `ActorTypeNPC` |
| 3 | FormFilters | `FormFiltersComponentParser` (`LookupConfigs.h:399-433`) | `NONE` |
| 4 | LevelFilters | `LevelFiltersComponentParser` (`LookupConfigs.h:435-485`) | `NONE` |
| 5 | Traits | `TraitsFilterComponentParser` (`LookupConfigs.h:487-541`) | `-C` |
| 6 | Count (or package index) | `IndexOrCountComponentParser` (`LookupConfigs.h:543-573`) | `1` (Keyword line: `NONE`, section 13) |
| 7 | Chance | `ChanceComponentParser` (`LookupConfigs.h:575-591`) | `100` |

(Column "Ours" is the `Item` line; the `Keyword` line has `KEFEquip_0x800_CardboardFaceMask_esp` in
section 1 and otherwise the same values.)

More than 7 sections throws "Too many sections" (`Parser.h:70-72`); missing trailing sections are
passed as empty strings (`Parser.h:79-82`). `NONE` (any case) and empty both mean "not set"
(CLibUtil `distribution.hpp:76-84`).

## 3. FormID of a record in an ESL-flagged plugin: `0x800~CardboardFaceMask.esp` is correct

* A section containing `~` is a FormID+plugin pair: it is split on `~` and the left part parsed as
  hex with `std::stoul(..., 16)` (which accepts the `0x` prefix) (CLibUtil `distribution.hpp:86-117`,
  `string.hpp:123-139`).
* Lookup: `dataHandler->LookupForm(formID, modName)` (`FormData.h:217-224`), implemented in
  CommonLibSSE-NG `src/RE/T/TESDataHandler.cpp:113-141`:
  `formID = compileIndex << 24` + `smallFileCompileIndex << 12` + the given local ID. For a light
  (ESL-flagged) plugin `compileIndex` is `0xFE`, so `0x800` becomes the runtime ID `0xFExxx800`; for
  a regular plugin `smallFileCompileIndex` is 0 and the same line still works. The plugin name is
  matched case-insensitively (`TESDataHandler.cpp:176-185`, `_strnicmp`).
* Therefore the ini must contain the **local** ID (`0x800`, no `FE`/load-order prefix). An ESL may
  only define object IDs 0x800-0xFFF; ours are 0x800-0x802 (checked by `src/07_package.py`).
* Unknown IDs are logged as `[0x800] (CardboardFaceMask.esp) FAIL - formID doesn't exist`
  (`FormData.h:622-623`).

## 4. EditorID lookup of an ARMO needs powerofthree's Tweaks

* An entry without `~`, without `.es` and not pure hex is an EditorID (CLibUtil
  `distribution.hpp:86-98`); for non-keyword forms SPID calls `RE::TESForm::LookupByEditorID`
  (`FormData.h:243-262`), which searches the game's global EditorID map
  (CommonLibSSE-NG `include/RE/T/TESForm.h:202-241`).
* The game only fills that map for form classes whose `SetFormEditorID` virtual is overridden. The
  base implementation is a no-op (`TESForm.h:176`, `// 33 - { return true; }`). Classes that override
  it in CommonLibSSE-NG: BGSHeadPart, BGSKeyword, BGSMusicType, BGSSoundDescriptorForm, BGSVoiceType,
  TESGlobal, TESIdleForm, TESImageSpaceModifier, TESObjectANIO, TESObjectCELL, TESQuest, TESRace,
  TESSound, TESTopic, TESWorldSpace. **TESObjectARMO is not among them.** CLibUtil's own list of
  types that keep EditorIDs without help (`editorID.hpp:11-39`) also omits Armor, and falls back to
  po3_Tweaks' exported `GetFormEditorID` for everything else (`editorID.hpp:40-48`).
* powerofthree's Tweaks ("Load EditorIDs", `bLoadEditorIDs`, default on: po3-Tweaks
  `src/Settings.h:81`) hooks vfunc 0x33 of TESObjectARMO and others (`src/Fixes/CacheEditorIDs.cpp:54`)
  and inserts each EditorID into the same global map (`src/Cache.h:25-42`).
* Conclusion: `Item = FaceMaskArmor` would fail with `(FaceMaskArmor) FAIL - editorID doesn't exist`
  (`FormData.h:632-633`) unless Tweaks is installed. We use the FormID form, which needs no Tweaks.
  SPID logs whether Tweaks was found: `powerofthree's Tweaks (po3_tweaks) detected : ...`
  (`main.cpp:30-31`).

## 5. String filters: what `ActorTypeNPC` matches

* Parsing (`LookupConfigs.h:367-397`): the section is split on `,`; an expression containing `+` goes
  to **ALL**, one starting with `-` to **NOT**, one starting with `*` to **ANY** (partial match),
  anything else to **MATCH**. Only one modifier per expression.
* Evaluation (`LookupFilters.cpp:17-36`): fail if not every ALL term matches; fail if any NOT term
  matches; fail if MATCH is non-empty and no MATCH term matches; fail if ANY is non-empty and no
  partial match. So terms in one section are OR-ed, `-` exclusions are always AND-ed
  (`A,B,-X` = (A or B) and not X; the reference says the same, lines 232-241).
* A term matches (`LookupNPC.cpp:86-104`, case-insensitive `iequals`) when it equals
  - the EditorID of a keyword on the NPC (`LookupNPC.cpp:45-48`) **or on its race**
    (`LookupNPC.cpp:65-70`), including keywords SPID distributed earlier, also in the same pass
    (`Distribute.h:192` inserts each distributed keyword into the NPC data that later entries'
    filters read, `LookupNPC.cpp:86-91, 117-120`);
  - the NPC's display name (`LookupNPC.cpp:39`, `actor->GetName()`);
  - the EditorID of the NPC, its template or leveled base (`LookupNPC.cpp:7-10, 50-63`). NPC_
    EditorIDs come from `editorID::get_editorID`, i.e. they are only available with po3 Tweaks.
* Keyword EditorIDs are always available: BGSKeyword overrides `SetFormEditorID` and stores the
  string in the form (`include/RE/B/BGSKeyword.h:30`). So `ActorTypeNPC` is matched against keyword
  EditorIDs and works without Tweaks; in vanilla it is a race keyword, which is why it selects
  humanoid NPCs.
* Sections are AND-ed with each other; chance is rolled first, then string, form, level and trait
  filters are tested (`LookupFilters.cpp:196-230`).

## 6. Traits: `-C` excludes children

* `-C` sets `traits.child = false`; `C` sets it to true; `/` combines traits; also `M F U S L T D`
  and their `-` forms (`LookupConfigs.h:487-541`).
* Test: `if (traits.child && a_npcData.IsChild() != *traits.child) fail` (`LookupFilters.cpp:161-163`)
  with `child = actor->IsChild() || race->formEditorID contains "RaceChild"` (`LookupNPC.cpp:41`;
  TESRace keeps its EditorID, `include/RE/T/TESRace.h:309`). So yes, `-C` keeps the mask off children.

## 7. Count and chance

* Count: `N` -> exactly N, `min-max` -> random in range; default 1 (`LookupConfigs.h:543-573`,
  default at `LookupConfigs.h:103`). For items the counts of every matching line for the same form are
  **added** (`Distribute.h:134-153`), so two matching `Item` lines would give two masks.
* Chance: percent, stored as fraction (`value / 100`, `LookupConfigs.h:575-591`), default 1.0
  (`Defs.h:111-125`); with `value >= 1` no roll is made (`LookupFilters.cpp:199`).
  - Plain chance (`25`): a fresh `RNG().generate()` every time an NPC is processed
    (`LookupFilters.cpp:210`), i.e. once per NPC per game launch (section 8), so **different NPCs get
    masks after every restart** (the reference says the same, `SPID Complete Reference.txt:572`).
  - Deterministic chance (`25!`, trailing `!`: `LookupConfigs.h:579-581`): the seed combines a hash
    of the whole entry text (`LookupConfigs.cpp:73-74`), the current player character's ID and the
    actor's FormID (`LookupFilters.cpp:201-208`), so the same NPCs get masks every launch for the
    same character; editing the line or starting a new character reshuffles them (reference lines
    574-582). Each roll logs `Seed for Actor ...` at info level (`LookupFilters.cpp:207`).
  - For a cosmetic mask a stable choice is what one expects, so `src/07_package.py` writes
    `chance_percent` below 100 with `!` (`chance_field`). `chance_percent` must be in (0, 100].

## 8. When SPID distributes, and to whom

* Hooks on `Character` vfuncs `ShouldBackgroundClone` (0x6D) and `InitLoadGame` (0x10)
  (`DistributeManager.cpp:24-96`): distribution runs when an actor is loaded, once per base NPC per
  game session (a runtime `SPID_Processed` keyword, `DistributeManager.cpp:13-22, 99-106`).
* **The player is never processed**: `should_process_NPC` returns `!a_npc->IsPlayer() && !IsDeleted()`
  (`DistributeManager.cpp:8-11`). `config.yaml: distribute_to_player` therefore has no effect; use the
  console to try the mask yourself.
* Dead NPCs are processed too unless the line has `-D` (`Distribute.cpp:197-199`). KEF, however,
  skips actors that are dead when it first sees them (`KEF src/main.cpp:46-48`), so NPCs found
  already dead (placed corpses) carry an unworn mask in their loot. Adding `-D` would not be a
  safe fix: SPID processes each *base* NPC once per session, so a dead first actor would cost the
  living actors of the same base their copy.
* The `ActorTypeNPC` string filter also selects mannequins: vanilla ManakinRace
  (`0x10760A` in `Skyrim.esm`; Mutagen.Bethesda.FormKeys.SkyrimSE 3.4.0 `Skyrim.Race.ManakinRace`,
  and F02K/Frostfall-Server @91c1694 `skyrim-esm-references/races.json`, keywords
  `["ActorTypeNPC"]`) carries the keyword, and string filters match race keywords
  (`LookupNPC.cpp:65-70, 93-104`). No armature lists ManakinRace (`src/plugin/Generator/Vanilla.cs`),
  so the mask is probably invisible on mannequins. The shipped lines keep `NONE` form filters (the
  lines are fixed in CLAUDE.md); the ini has a commented pair with `-0x10760A~Skyrim.esm`
  (section 12).
* Nothing is written to the save by SPID itself: distribution is redone from scratch on every launch
  (reference lines 63-64).

## 9. Is the distributed armor equipped? Where?

* For `Item` entries SPID only **adds the object to the base NPC's container**:
  `npc->AddObjectsToContainer(a_objects, npc)` (`Distribute.cpp:94-105`), implemented in
  CommonLibSSE-NG `src/RE/T/TESContainer.cpp:63-82` (adds a ContainerObject or raises its count).
* SPID contains **no equip call for items**. The only `ActorEquipManager::EquipObject` call in SPID is
  in the outfit code (`Outfits/Helpers.h:24`), used for `Outfit =` entries.
* SPID used to equip distributed weapons and armor: that code (`DistributeItems`, calling
  `ActorEquipManager::EquipObject` for every new weapon/armor) was removed in commit `c94d422`
  ("revert item equipping", 2024-03-13, `git show c94d422 -- SPID/src/Distribute.cpp`). Guides
  written before that may still say SPID items are worn.
* Whether the engine then puts the mask on by itself is closed-source behaviour and **cannot be
  verified offline**; users report that SPID-distributed armor stays in the inventory unworn (KEF's
  page says the same: NPCs "will just let it sit there unequipped"). So by
  default the mask is equipped through KEF (section 13). With `equip_method: engine` nothing equips
  it: NPCs may just carry it (step 3 of docs/TESTING.md shows which).
* Conditions that can still keep a mask off a face, to check in game: the race is not covered by
  either armature (the item is worn but invisible), another worn item already uses slot 55 (KEF
  then skips the NPC unless the keyword ends in `_forceEquip_true`, section 13), the
  `non_playable` flag (config.yaml warns to test it before enabling), or a mod that re-applies
  outfits.
* Can NPCs unequip it? SPID never equips items (it passes `false` for "prevent removal", the equip
  flag that locks a slot, even for outfits: comment at `Outfits/Helpers.h:21-23`, call at
  `Outfits/Helpers.h:24`). KEF does set it: `EquipObject(actor, item, nullptr, 1, nullptr, false,
  true, false, true)` (`KEF src/main.cpp:207`), whose 7th parameter is `a_forceEquip`
  (`KEF-CL include/RE/A/ActorEquipManager.h:19`), the flag SPID's comment calls prevent removal.
  The mask can still be pickpocketed, traded or looted while it is playable.
* `Skin =` would replace the NPC's body skin (`Distribute.cpp:107-115`) and `Outfit =` would replace
  the whole outfit, so neither is suitable here.

## 10. Log

* File: `<Documents>\My Games\Skyrim Special Edition\SKSE\po3_SpellPerkItemDistributor.log`. The
  name is the CMake project name (`SPID/CMakeLists.txt:2,57`; `main.cpp:102-113`); the folder is
  CommonLibSSE-NG's `log_directory()` (`src/SKSE/Logger.cpp:71-93`: Documents/My Games/
  "Skyrim Special Edition", or "... GOG" without `steam_api64.dll`, + `SKSE`). Under CrossOver this is
  inside the bottle's `drive_c/users/<user>/Documents/`.
* Log level: `Data\SKSE\Plugins\po3_SpellPerkItemDistributor.ini`, `[Log] LogLevel`
  (trace/debug/info/...), default `info` (`main.cpp:115-130`).
* What to look for:
  - `INI` section listing `CardboardFaceMask_DISTR.ini` (`LookupConfigs.cpp:101,106`);
  - `Registered x/y Items` with x = y after lookup (`LookupForms.cpp:97-107`; `1/1` when no other
    mod distributes items); x < y plus a `FAIL - formID doesn't exist` line naming
    `CardboardFaceMask.esp` means the plugin is not active or the ID is wrong (`FormData.h:622-623`);
  - `Registered x/y Keywords` likewise for the `Keyword` line (same code, record name `Keyword`,
    `LookupConfigs.h:70`); a keyword that cannot be created logs
    `KEFEquip_0x800_CardboardFaceMask_esp FAIL - couldn't create keyword` (`FormData.h:628`);
  - per NPC: `[📦] Distribution for <actor>` followed by a type line `ARMO` with
    `"Cardboard Face Mask" [ARMO:FExxx800] @ CardboardFaceMask_DISTR.ini` and a type line `KYWD` with
    `KEFEquip_0x800_CardboardFaceMask_esp [KYWD:xxxxxxxx] @ CardboardFaceMask_DISTR.ini`
    (`Distribute.cpp:164, 211-236`; form text from `Defs.h:181-203`, which prints an EditorID when
    one is known - a keyword always has one, the ARMO only with po3's Tweaks - and a name when there
    is one: a `BGSKeyword` derives from `TESForm` only, so it has none, CommonLibSSE-NG
    `include/RE/B/BGSKeyword.h:9`, `src/RE/T/TESForm.cpp:28-37`; `KYWD` from
    `src/RE/F/FormTypes.cpp:17`). Logged at `info`, the default level.
* An ini line that cannot be parsed (too many `|` sections: `Parser.h:70-72`; a bad count or chance:
  `LookupConfigs.h:571, 588`; an unsupported key: `LookupConfigs.h:350`) throws a `std::exception`
  that the per-entry `TryParse` catches: it only logs
  `Failed to parse entry [Item = ...]: <reason>` at warn level and skips the line
  (`LookupConfigs.cpp:85-87`). The line then also has no `Registered x/y Items` count, which is printed
  only for record types that have entries (`LookupForms.cpp:101-106`), at data load, i.e. when the
  main menu is reached (`main.cpp:56-58`).
* **A line SPID cannot parse produces no message in game.** The only in-game text SPID prints is a
  console line, `[SPID] Errors found when reading configs. Check po3_SpellPerkItemDistributor.log in
  ...` (`RE::ConsoleLog::Print`, `main.cpp:62-65`, the only console/message-box call in SPID's
  source; a console line, not a message box), and only when
  `shouldLogErrors` is set. That flag is set only in the outer `catch (...)` of `GetConfigs`
  (`LookupConfigs.cpp:143-146`), which an `Item`/`Keyword` parse error never reaches: `TryParse`
  catches every `std::exception` itself (`LookupConfigs.cpp:85-87`), and so do the exclusive-group,
  linked and death parsers that see the line first (`ExclusiveGroups.cpp:56-62`,
  `LinkedDistribution.cpp:102-107`, `DeathDistribution.cpp:79-81`). So the signals for a broken
  line are a `Failed to parse entry` warning, or a missing/short `Registered x/y ...` line, in the
  SPID log.
* `Registered x/y Items` counts the `Item` lines of **all** `_DISTR` files together
  (`LookupForms.cpp:97-106`): x = y means every one resolved; with no other item distributor it is
  `1/1` (the same holds for `Keywords`).

## 11. Supported game versions (SPID 7.3.3)

* Built with CommonLibSSE-NG for SE and AE, VR off (`SPID/CMakeLists.txt:18-20`).
* `SKSEPlugin_Version`: `UsesAddressLibrary()`, `UsesUpdatedStructs()`,
  `CompatibleVersions({ RUNTIME_SSE_LATEST })` (`main.cpp:139-149`); the pinned CommonLibSSE-NG sets
  `versionIndependenceEx = kVersionIndependentEx_AddressLibraryV5` by default
  (`include/SKSE/Interfaces.h:422`) and knows runtimes up to 1.7.99 (`include/SKSE/Version.h:36-40`).
  `SKSEPlugin_Query` is exported too (`main.cpp:151-157`) for the 1.5.97 (SE) loader.
* SKSE64 treats an Address-Library plugin with the V5 flag as version independent and skips the
  `compatibleVersions` list (skse64 `skse64/PluginManager.cpp:541-615`), provided
  `Data\SKSE\Plugins\versionlib-<runtime>-0.bin` exists; otherwise the plugin is disabled with
  "address library needs to be updated" (`PluginManager.cpp:427-454`).
* SKSE's current release targets runtime 1.7.104 with build 2.3.1 (skse64
  `skse64_common/skse_version.h:59,65-66`; skse.silverlock.org front page, 2026-10-03: "Current
  Anniversary Edition build 2.3.1 (game version 1.7.104)").
* Conclusion: SPID 7.3.3 should load on Steam 1.7.104 with SKSE 2.3.1 and an Address Library
  that contains `versionlib-1-7-104-0.bin`; also on 1.5.97 and 1.6.x. Not VR (separate SPID VR build).
  Whether the Nexus release is 7.3.3 could not be checked here (Nexus is not reachable).

`ActorTypeNPC` and `25!`). Form-filter exclusions use FormIDs so they never depend on EditorID
lookup. The race IDs are ArgonianRace 0x013740, KhajiitRace 0x013745, ArgonianRaceVampire 0x08883A
and KhajiitRaceVampire 0x088845, each confirmed by two sources in `tests/test_plugin.py`
(`SECOND_SOURCE`), and ManakinRace 0x10760A (Mutagen FormKeys 3.4.0 and the Frostfall dump,
section 8; `tests/test_plugin.py` `FORBIDDEN_RACES`).

## 13. Equipping: KEF

KEF ("KEF - Keyword Equip Framework", by ziman62,
<https://www.nexusmods.com/skyrimspecialedition/mods/185273>) is an SKSE plugin that makes NPCs
equip the item named inside a `KEFEquip_...` keyword. SPID distributes the keyword; KEF does the
equipping; neither needs Papyrus.

### What the SPID source proves (commit `6e66908`)

* **The keyword line is read like any other entry.** `Keyword` is a record type
  (`LookupConfigs.h:61-74`), parsed by the same seven section parsers as `Item`
  (`LookupConfigs.cpp:59-67`).
* **Section 1 is read as an EditorID.** CLibUtil `get_record_type` (`distribution.hpp:86-98`): a
  section containing `~` is FormID~plugin, one containing `.es` is a plugin name, one that is only
  `0x`+hex digits (`string.hpp:65-77`) is a FormID, anything else an EditorID.
  `KEFEquip_0x800_CardboardFaceMask_esp` has no `~`, no `.es` (written with `.esp` it would be
  taken for a plugin name, which is presumably why KEF's format uses `_esp`) and is not pure hex,
  so it is an EditorID. The `0x800` inside it and the underscores are not special. SPID
  sets no length limit (the name is a `std::string` copied into the keyword's `BSFixedString`,
  `FormData.h:186`). Characters that would break it: `|` (section separator, `Parser.h:67`), `~`,
  `.es`, `0x` followed by two or more zeros anywhere (the sanitizer strips such leading zeros
  without a word boundary, `LookupConfigs.cpp:46-47`: `KEFEquip_0x00800_...` would be rewritten to
  `KEFEquip_0x800_...`), and, where the name is used as a string filter, `,` `+` and a leading `-`
  or `*` (section 5).
* **SPID creates the keyword** because no plugin defines it: for a `Keyword` entry the form is looked
  up with `kCreateIfMissing` (`FormData.h:608`); an EditorID goes to `find_or_create_keyword`
  (`FormData.h:247-248`), which searches all loaded keywords by EditorID and, if none matches, creates
  a new `BGSKeyword` with the form factory, sets its `formEditorID` and appends it to the data
  handler's keyword array (`FormData.h:170-197`). Failure logs `FAIL - couldn't create keyword`
  (`FormData.h:628`). This happens once, at data load (`main.cpp:56-60`).
* **The count is ignored**: the keyword branch of `for_each_form` never reads `idxOrCount`
  (`Distribute.h:185-203`), but the count is still parsed (`LookupConfigs.h:543-573`), so `NONE`
  (as in KEF's own example) is the clean value.
* **The keyword goes onto the NPC's base record**: `npc->AddKeywords(a_keywords)` on the `TESNPC`
  (`Distribute.cpp:15-19`; CommonLibSSE-NG `src/RE/B/BGSKeywordForm.cpp:32-40` copies the keyword
  array with the new ones appended). Every actor of that base NPC then has it, like the item. It is
  runtime only, redone every launch (section 8), and logged as a `KYWD` line (section 10).
* **Order**: within one distribution pass SPID adds keywords first and items later
  (`Distribute.cpp:15-19` before `94-105`; the reference lists the same order, `SPID Complete
  Reference.txt:84-99`). Both happen in the same call from the actor-load hooks
  `ShouldBackgroundClone` / `InitLoadGame` (`DistributeManager.cpp:28-76`); the `InitLoadGame` path
  only runs when the actor's 3D is already loaded (`DistributeManager.cpp:70-73`).
* **Chance**: two lines with the same `25!` roll independently, because the deterministic seed
  starts from a hash of the whole entry text (`LookupConfigs.cpp:73-74`, `LookupFilters.cpp:201-208`),
  which differs between the `Item` and the `Keyword` line. That is why below 100 % the generator puts
  the chance on the `Keyword` line only and gives the `Item` line the keyword as its string filter
  at 100 %: the keyword is added first and string filters of later entries see it
  (`Distribute.h:192`, `LookupNPC.cpp:86-91, 117-120`), so exactly the NPCs with the keyword get the
  mask.

### What KEF's source says (commit `0fb5244`)

KEF's Nexus page could not be opened here (HTTP 403); search-engine extracts of it gave the keyword
format and examples. Its source settles the rest. That the Nexus DLL is built from this source is
an inference, but a strong one: `xmake.lua` names the project `KeywordEquipFramework` (author
`ziman99`; the Nexus author is ziman62), and the commit history matches the Nexus changelog (leveled-list
support = v3, "Update commonlibng version" 2026-08-29 = v4 "Update to alandtse commonlibng
version", "Update commonlibng" 2026-08-30 = v5 and the page's last update). The predecessor repo
Teijirr/SkyrimKeywordEquipFramework (`1de459e`) has the same logic in `src/plugin.cpp`.

* **When it runs**: a hook on `Character` vfunc `0x6A` (`KEF src/main.cpp:219-240`), which is
  `Load3D` (`KEF-CL include/RE/T/TESObjectREFR.h:286`), calls `ProcessKEFKeywords` after the 3D
  loaded. The hook is installed at `kDataLoaded` (`main.cpp:245-257`).
* **Once per actor per game session**: a static `g_ProcessedActors` set (`main.cpp:9`); an actor
  already in it returns at once (`main.cpp:41-43`); every processed actor is added at the end,
  equipped or not (`main.cpp:216`), and dead or keyword-less actors are added immediately
  (`main.cpp:46-48`). Nothing clears the set (its only uses are lines 9, 41, 47, 216; the
  `kPreLoadGame`/`kPostLoadGame` cases are empty, `main.cpp:258-263`). SPID's base-container mask
  and keyword stay for the whole session too (section 8). So after loading a save **without
  quitting** (death reload, older save), NPCs KEF already handled in that session whose saved state
  lacks the worn mask keep SPID's copy unworn until the game is restarted; a new 3D load (leaving
  the cell) does not help.
* **Dead actors are skipped** (`main.cpp:46`), see section 8.
* **Keyword parsing** (`main.cpp:78-102`): the text after `KEFEquip_` (9 characters), an optional
  `_forceEquip_true` / `_forceEquip_1` suffix cut off at its last occurrence, then FormID = text
  before the first `_`, plugin = text between the first and the last `_`, extension = text after
  the last `_`. `KEFEquip_0x800_CardboardFaceMask_esp` gives `stoul("0x800", 16)` = 0x800 and
  `CardboardFaceMask.esp`; underscores inside the plugin name are kept.
* **Lookup**: `TESDataHandler::LookupForm(0x800, "CardboardFaceMask.esp")` (`main.cpp:117`), which
  in the pinned CommonLib builds `compileIndex << 24` + `smallFileCompileIndex << 12` + the local ID
  (`KEF-CL src/RE/T/TESDataHandler.cpp:125-140`), i.e. the correct ID for an ESL-flagged plugin.
  A failure logs `Failed to resolve form [800] from plugin CardboardFaceMask.esp` (`main.cpp:120`).
* **Occupied slot**: without `forceEquip`, if the actor already wears an armor in the item's slot
  mask, KEF does nothing for it (`main.cpp:178-188`): no copy added, nothing equipped.
* **Adding**: KEF counts the item in `a_actor->GetInventory()` (`main.cpp:51, 167-176`), which
  includes the base NPC's container (`KEF-CL src/RE/T/TESObjectREFR.cpp:423-472`,
  `ForEachContainerObject ... it->second.first += a_entry.count`), where SPID's `Item` line put the
  mask in the same pass that added the keyword (section 9). It adds a copy only when the count is
  `<= 0` (`main.cpp:194-199`). So with both lines each NPC carries **one** mask, worn; the `Item`
  line still supplies the carried mask when slot 55 is taken, and keeps `equip_method: engine`
  meaningful.
* **Equipping**: `EquipObject(actor, item, nullptr, 1, nullptr, false, true, false, true)`
  (`main.cpp:207`): not queued, `a_forceEquip` = true (prevent removal, section 9), no sound, apply
  now. Then it logs `SUCCESS - Item <name> equipped on actor <name>` (`main.cpp:209`).
* **Log and DLL name**: the xmake target and plugin name are `KeywordEquipFramework`
  (`xmake.lua:2, 38-47`), so the DLL is expected as `KeywordEquipFramework.dll`; CommonLib's
  `SKSE::Init` opens `<SKSE log folder>/<plugin name>.log` by default (`KEF-CL
  include/SKSE/API.h:15`, `src/SKSE/API.cpp:97-98`, `src/SKSE/Logger.cpp:126-135`), i.e.
  `KeywordEquipFramework.log`.
* **Runtime 1.7.104**: the pinned CommonLib's plugin declaration defaults are
  `StructCompatibility::Independent` at offset 0x300 (= `versionIndependenceEx`
  `kVersionIndependentEx_NoStructUse`) and an address-library `RuntimeCompatibility` at 0x304
  (= `kVersionIndependent_AddressLibraryPostAE`) (`KEF-CL include/SKSE/Interfaces.h:370-378,
  533-586, 620, 631, 642-643`), without the V5 bit. SKSE 2.3.1 demands the V5 bit only from DLLs
  built before 2025-05-26 (skse64 `PluginManager.cpp:564-576`) and accepts NoStructUse for the
  1.6.629 struct check (`PluginManager.cpp:580-588`); the pinned CommonLib also reads the new
  address-library format (`KEF-CL src/REL/IDDB.cpp:158`). So a DLL built from this source on
  2026-08-30 should load on 1.7.104 when `versionlib-1-7-104-0.bin` is installed.
* License: GPL-3.0 (`LICENSE`, `xmake.lua:6`).

From the Nexus page (search extracts, 2026-10-03; consistent with the source): the format
`KEFEquip_0x[FORMID]_[MODNAME]_[EXTENSION]`, the example `KEFEquip_0x800_MyCoolAmulet_esp`, the
second example `KEFEquip_0x803_Kad_AkaviriHats_esp_forceEquip_true` (plugin `Kad_AkaviriHats.esp`),
"compatible with all Skyrim versions (SE, AE, VR)", and that KEF complements outfits with
accessories rather than replacing outfits.

The generator still accepts only letters and digits joined by single `_` for the plugin stem
(`KEF_MODNAME_RE`) and refuses `_` parts named `esp`, `esm`, `esl` or `forceEquip`: the source
would mis-split a stem containing `_forceEquip_`, and dots or spaces were never needed.
`CardboardFaceMask` is unaffected.
